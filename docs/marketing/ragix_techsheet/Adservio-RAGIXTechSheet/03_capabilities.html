3. The capability catalogue

RAGIX organises its work into nine families of kernels, 101 registered kernels in all. Each family is a coherent business capability — best understood as a verb the platform performs on your corpus. They share a common engine and a common audit trail, so an organisation that adopts one family can extend to the others without changing its tooling or its governance.

3.1 One pipeline, three stages

Every family follows the same disciplined three-stage pipeline. This shared shape is what makes the platform predictable, parallelisable and easy to govern: each stage produces an inspectable result before the next begins.

1. Collection — parse, extract, inventory 2. Analysis — measure, cluster, score 3. Reporting — synthesise & render

Collection and analysis are almost entirely deterministic; language models enter only at the reporting stage, and even there their output is checked. The generative families are the exception: in Reviewer, Translate and the authoring part of Summary the model writes content, so they guarantee reproducibility instead (greedy decoding, a pinned model, a recorded prompt version). Independent kernels within a stage run in parallel, which is why a 60,000-line codebase can be fully analysed in a handful of seconds.

3.2 Understanding code: the Audit family

The Audit family reads a Java or JEE codebase down to its abstract syntax tree and produces a complete, quantified health assessment: complexity hotspots, dead code, architectural coupling, dependency structure, service topology and a risk matrix. It also measures drift — the distance between what the documentation claims and what the code actually does — which is the heart of the "does the code match the spec?" question. Results are deterministic and arrive in seconds, not weeks.

3.3 Digesting documents: the Docs and Summary families

The Docs family ingests large mixed-format corpuses, extracts the facts, requirements and definitions they contain, and builds hierarchical, citeable summaries — corpus, domain, cluster and document levels — so a reader can move from a one-page overview to a precise source passage in a few clicks. The Summary family adds Graph-RAG consolidation across many sources and a tiered redaction model, so the same corpus can be released at public, internal or audit-only sensitivity without re-running the analysis.

Docs — digest & summarise
  • Ingests PDF, Office and Markdown at corpus scale
  • Extracts facts, rules and definitions with provenance
  • Builds four-level hierarchical summaries
  • Detects gaps, overlaps and version drift
Summary — compare & consolidate
  • Merges sources only along genuine provenance links
  • Keeps versions and origins distinct
  • Tiered redaction: public / internal / audit
  • Visual drift maps between releases

3.4 Producing deliverables: Reviewer & Presenter

The platform does not stop at analysis; it produces the finished artefact. The Reviewer family edits long documents chunk by chunk — fixing errors, flagging inconsistencies — while logging and numbering every change so any edit can be reverted independently. The Presenter family turns a long report into a polished slide deck, at a level of compression you choose, from a full technical deck to a 25-slide executive summary.

Reviewer — review & edit
  • Edits documents beyond any context-window limit
  • Every change numbered, reasoned and reversible
  • Protected regions (code, maths, tables) untouched
  • A fast model proposes; a stronger model validates
Presenter — generate decks
  • Long report → finished slide deck, reproducibly
  • Full, compressed or executive compression modes
  • Professional theme, diagrams, PDF and HTML output
  • Companion handouts and glossaries on demand

3.5 How a RAGIX document is written: facts first, prose last

It is worth being precise about how RAGIX writes a deliverable, because it is the opposite of asking a model to "draft a report". The document is built outward from verified material: the corpus is first reduced to structured, citeable facts; the kernels then assemble the document's skeleton — its sections, tables, figures and every number — by computation; and only at the very end does a model add the connective prose around content that is already true. A second model verifies that prose against the facts, and protected regions (figures, tables, code, mathematics) are never rewritten.

Extract citeable facts Compute tables & figures Assemble the structure Write prose around facts Verify & lock

This is not a future ambition: the deliverables from Adservio's field engagements were produced this way. Each artefact below is machine-generated, with its numbers and tables computed rather than written, and each statement traceable to a source.

3.6 Guarding the perimeter: Security and the Pentest lab

The Security family scans dependencies, configuration and source for known vulnerabilities, exposed secrets and compliance gaps, and maps findings to recognised control frameworks. Because it runs locally like every other family, it can be applied to material that could never be uploaded to an external scanning service.

Since version 0.74 it is complemented by RAGIX-Pentest, a rootless, containerised lab for the defensive assessment of systems you own or are explicitly authorised to test. The kernels measure a posture; the lab is where a weakness is reproduced and its remedy checked. The repository ships the framework only, never engagement data.

Security kernels — measure
  • 11 kernels: discovery, vulnerability assessment, compliance
  • Run on the host, inside your perimeter
  • Findings mapped to control frameworks
Pentest lab — validate & remediate
  • Tools in a pinned container image, no host privilege
  • A scope allow-list refuses any target not listed; an empty list refuses all
  • Every run appended to the engagement's audit trail
  • Engagement data kept outside the engine's tree

Authorised defensive use only. The scope gate is a safety aid; it does not replace a written authorisation to test.

3.7 Reading documents: Saqqara, the document substrate

Saqqara is the part of RAGIX that reads documents. It turns PDF, Word, Excel, PowerPoint and Markdown files into one kind of object, a typed tree, and keeps on every node the exact place it came from: the page and position, the cell, the paragraph, the slide or the line. It recognises sections, tables, header bands and label columns by ordered, tested rules, and no language model runs anywhere in it. The trees are stored in a single SQLite file and searched on a lexical lane and, when an embedding model is configured, on a dense lane; every hit leads back to the nodes it came from.

0 Language-model calls
5 Formats read natively
6 Kernels
154 Propositions, each tested

Saqqara is a family like the others, with the same kernel contract, registry, orchestrator and MCP server, and it is the substrate under the families that need exact citations. Its document Explorer, four kernels, takes a census of a corpus, profiles it, reads its tables and reports what it found, with the sources of every line. The Harvest library builds those reading reports from Saqqara's readings.

3.8 Preparing responses: the Tender family

Tender works over a store that Saqqara built. It never builds a store, never reads a source file and never writes to what it reads, the last checked on the database file's hash across a run. It holds one kernel today, a probe; the kernels that recover the questions a document asks and draft only from evidence selected first are to come.

Saqqara has its own tech sheet, a dossier and a deck, with measurements on public documents and a comparison with Docling: docs/marketing/saqqara_techsheet/ in the RAGIX repository.

3.9 Translating: the Translate family

KOAS-Translate translates long technical and scientific documents, currently from English to French, in six stage kernels: extract, segment, draft, quality check, harmonise and rebuild. Equations, code, citations, URLs and Markdown structure are carried verbatim, and a translation memory makes a long run resumable. Inference is local. Because the model writes the translation, the family guarantees reproducibility (greedy decoding, a pinned model digest, a recorded prompt version) rather than bit-exact output. Other language pairs, and access from the command line and MCP, are pending.

3.10 Confidential documents: RAGIX-Sealed

RAGIX-Sealed lets local kernels inventory, analyse and report on a confidential corpus without any raw content reaching a language model. Its boundary lies between the human and the model, not between the human and the system: the authorised operator sees everything, and no model ever does. The original is sealed (AES-256-GCM, bound to its case, document, policy and state), sensitive values are replaced by role-aware placeholders, the result is leak-scanned, and only this cooled content is indexed and reasoned over. Re-identification is a human path, authorised and audited, and never feeds a model.

STATUS: DRAFT v0.1

The roadmap of RAGIX-Sealed is implemented and tested, including a red-team suite that sweeps seeded canary secrets across every public surface. Named-entity recognition, durable persistence and signed, expiring authorisations remain to be built before production use.

3.11 How you operate it

The same capabilities are reachable through whichever interface suits the user, all backed by the identical kernels and the identical audit trail.

For automation

Composable command-line tools for each family fit naturally into CI/CD pipelines and scripted, repeatable engagements.

For AI orchestration

A standard tool protocol exposes the platform to assistants such as Claude, so an AI can run an analysis without ever seeing the content — the subject of the next section.
